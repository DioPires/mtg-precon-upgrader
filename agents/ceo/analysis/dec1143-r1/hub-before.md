## Why
- **Scryfall's limits** (`https://scryfall.com/docs/api/rate-limits`, read by me on 2026-10-13): `/cards/named`, `/cards/search`, `/cards/random` and `/cards/collection` allow 2 requests a second each. Every other method allows 10 a second. The image host `*.scryfall.io` has no limit. A 429 limits the caller for 30 seconds. The page says "It is not acceptable to ignore HTTP 429 responses", and an application that keeps overloading the API can be banned.
- **The app sends one `/cards/named` lookup every 120 ms** (`web/src/data/cardCache.ts:40`, `THROTTLE_MS`). The comment at `:13-14` cites an older guideline of 50 ms between calls. /shopping sent 88 lookups in 11.6 s, which is 7.6 a second (DEC-1045 baseline, comment `e6d99397`).
- **A 429 does not stop the app.** `fetchOne` waits for `retry-after`, or 750 ms and then 1,500 ms, and tries the same card up to three times (`cardCache.ts:180-190`). `ERROR_RETRY_MS` at `:41` is 30 s. I have not read what the queue does meanwhile: item 2.
- **Two components send image lookups on the same method, outside the queue:** `web/src/components/global/GV1CardHoverLayer.tsx:19` (`format=image&version=large`, one for each hover) and `web/src/components/molecules/GV1CommanderArt.tsx:16` (`format=image&version=art_crop`).
- `web/src/data/cardAtlas.ts:164` calls `/cards/autocomplete`, which allows 10 a second.
- **The requests leave the user's browser.** The owner uses the app from the address that the deck work's card tools use. A limit or a ban on that address stops both.
- In the baseline run on `main` (two workers), Scryfall rejected 1,158 of 1,280 card lookups (90 %). What one user with one page gets is not measured yet: item 1.
- The e2e stub (PR #19, merged at `a645b74`) never answers 429, so no case shows this fault.
