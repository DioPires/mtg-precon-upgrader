# Tools

## Paperclip API (local instance)

- Base URL: `$PAPERCLIP_API_URL` (http://127.0.0.1:3100); auth via `Authorization: Bearer $PAPERCLIP_API_KEY` (env, short-lived JWT per run).
- Issue UUID for the current wake: `PAPERCLIP_WAKE_PAYLOAD_JSON` → `.issue.id` (DEC-### identifiers do NOT resolve in API paths).
- Post comment: `POST /api/issues/{uuid}/comments` with `{"body": "..."}`.
- Set status: `PATCH /api/issues/{uuid}` with `{"status": "done" | ...}`.
- Route-shape gotchas: see memory `reference_paperclip_api_route_shapes`.
- Checkout: `POST /api/issues/{uuid}/checkout` needs `{"agentId": "<my id>", "expectedStatuses": ["in_review", "in_progress", "todo"]}`; an empty body returns 400. Checkout sets the status to `in_progress` (an `in_review` park is lost until you PATCH it back), so read the thread before checking out an issue that is not this wake's (DEC-1015, 2026-10-13).
- Park an issue with a fallback monitor: `{"status": "in_review", "executionPolicy": {"monitor": {"nextCheckAt": "<ISO>", "scheduledBy": "assignee", "notes": "<500 chars"}}}`. `scheduledBy` accepts only `assignee` or `board`; any other value fails the whole PATCH with 400 (DEC-1019, 2026-10-13).
- Clear a fallback monitor in the same PATCH as a reassignment: `{"assigneeAgentId": "...", "status": "todo", "executionPolicy": {"monitor": null}}` (200, verified 2026-10-13).
- A monitor wakes the assignee (reason `issue_monitor_due`) only while the issue is `in_progress` or `in_review` with an agent assignee; `todo` + monitor wakes nobody. The CEO heartbeat is off (`wakeOnDemand` only), so a hand-back to the CEO itself needs a monitor or an assignment change (DEC-1014, 2026-10-13).
- `GET /api/issues/{uuid}/runs` lists runs newest-first (`runId`, `agentId`, `status`, `startedAt`, `errorCode`; there is no `id` key, so a `KeyError` here is a crashed read, not an empty list: retry it, never route on it); slice `[:n]`, never `[-n:]`. It holds every run that wrote to the issue, including a run woken elsewhere and the current run once it writes, so judge liveness by `id` ≠ own run and `status: running`. Before routing an issue outside the current wake, read its list and the thread: a live CEO run on it owns the routing (two wakes that fire together start two CEO runs; DEC-1015, 2026-10-13). A hand-back with no CEO run after it is a lost wake: route it now. The assignee's 422 fallback PATCH (assignee + `executionPolicy.monitor`) woke no CEO run on DEC-1015 (00:24Z, found at 01:07Z); its monitor fires about ten hours later, so sweep `in_review` issues on every wake.
- A board comment posted on many issues within a minute ("lets continue" on nine `in_review` issues, 2026-10-13 09:05–09:07Z) starts one CEO run per issue. Write only to the wake issue; a sibling issue with a live CEO run belongs to that run. Before ending, re-read the sibling's assignee and runs: route it yourself only if its run ended without the assignment (DEC-1002 / DEC-1012, 2026-10-13).
- Never end a turn on a background poll that waits for another run. The adapter fails the run (`adapter_failed`, liveness "unmanaged background task stopped; no durable live path") and Paperclip starts a recovery retry. When a sibling CEO run owns the close-out, check the state inline, then set a real disposition on the wake issue before ending: `done` if every leg is complete, or `in_review` with a monitor (DEC-1010, run `14e58ca8`, 2026-10-13).
- A monitor fire is consumed even when the run it starts fails before any work (`errorCode: provider_quota` or `configuration_incomplete`); the issue is then `in_review` with `monitor: null` and no path. On every wake, read `GET /api/issues/{uuid}` for each `in_review` issue of mine and re-arm a null monitor (DEC-987, 2026-10-13).
- When the retry budget is spent, Paperclip posts a system comment ("bounded retry budget is spent") and moves the issue to `blocked` with no monitor. A `blocked` issue assigned to me whose newest comment is that note is a lost wake: sweep `blocked` with `in_review` on every wake (DEC-1010, 2026-10-13). A status PATCH on an issue another live CEO run holds returns 409 "Issue run ownership conflict"; post the record, leave the status to that run.
- A lost wake found during another issue's run gets a run of its own: PATCH that issue with `status: in_review` and a monitor whose `nextCheckAt` is about four minutes ahead, with notes that name the verdict comment and the next action. Both monitors set this way fired at the set second and each started a CEO run scoped to its issue, which can post cards there (DEC-1012 and DEC-1037 from the DEC-978 run, 2026-10-13 10:12Z). Check the runs list once after the time passes. This works only while no `scheduled_retry` run is queued on that issue. A wake for an issue with a queued retry is coalesced into that run (`GET /api/issues/{uuid}/diagnostics/wakes` shows `status: coalesced`): the monitor is cleared and nothing starts before the retry time. `POST /api/issues/{uuid}/scheduled-retry/retry-now` is board-only (403). Route such a hand-back inline instead: read its children, runs and newest comment, PATCH a monitor later than the retry time as the claim, then write (DEC-1004 and DEC-1048 from the DEC-1050 run, 2026-10-13 15:10Z).
- A `retry_failed_run` wake can list `completedActions: []` although the dead run wrote. Before any write, find its writes by its run id: `originRunId` on the issues it created, and the `runs` list and newest comments of the hub and of each issue it could have touched. On DEC-1044 the dead run `9fc72f59` had posted the fix leg on DEC-1017 and opened DEC-1045 (2026-10-13).
- An account outage (`claude_auth_required`, `configuration_incomplete`) leaves three things behind. (1) The system moves an engineer's issue to `blocked` with a "paused" comment; when the board accepts the Connect card a retry is queued and the status stays `blocked`: PATCH `todo` (200, the queued run stays; DEC-1017). (2) A "Connect Anthropic" card (`connection_intent`) stays pending on each issue whose run died, though one acceptance reconnects every agent: withdraw my own with `POST /api/issues/{uuid}/interactions/{id}/withdraw` and a `reason` (200, `cancelled`). (3) An engineer's `in_progress` issue whose run died gets no retry unless the board acts on that issue: after an outage, list the company's issues updated at the failure time and read their runs (DEC-1042 sat 80 min).
- A monitor PATCH on another agent's issue returns 403 ("Only the assignee agent or a board user can manage issue monitors"). To wake a report whose run died, post a short resume comment: it started an `issue_commented` run within a second (DEC-1042, 2026-10-13). A failed write still adds my run to that issue's `runs` list, so a liveness guard must skip my own run id.
- Interactions (`POST /api/issues/{uuid}/interactions`) can be created only on the run's own issue (`PAPERCLIP_TASK_ID`); another issue returns 422 `sourceRunId must belong to the same issue`. Each question allows at most one `freeText` option (400 otherwise). To put a card on a hub issue, wake on that issue first or host the card on the current one and point to it.
- A run that dies on provider auth (`errorCode: claude_auth_required`, "OAuth token revoked") leaves two things on its issue: the error text as a comment by me, and a pending `connection_intent` card ("Connect Anthropic", `human_only`). The retry (`retry_failed_run`) names the card under `unresolvedInteractionIds`. When the retry authenticates, the card is stale: `POST /api/issues/{uuid}/interactions/{id}/withdraw` with `{"reason": "..."}` returns 200 and `status: cancelled`. Withdraw only the card on the wake issue; a sibling issue's card belongs to its own retry (DEC-1039, 2026-10-13).
- Before repeating a failed run's step, learn which writes it finished: `GET /api/heartbeat-runs/{runId}/log` holds its commands and their output (grep the command), `GET /api/heartbeat-runs/{runId}` gives `contextSnapshot.issueId` (the wake's issue) and `/issues` lists the issues the run wrote to. On DEC-1039 the failed run had already run `update-branch`; the retry checked the new head's parents and tree against the reviewer's merge tree, read the ten jobs and merged pinned, with no second update (2026-10-13).
- The run log is paged: one GET returns about 256 kB and a `nextOffset`. Read on with `?offset=<nextOffset>` until `nextOffset` is null; page one can stop in the middle of a record, before the run's last writes. A board comment ("try again") after a `provider_quota` death starts an `issue_commented` run whose payload also lists `completedActions: []`. On DEC-1031 the dead run `0936dc78` had merged PR #10, swept the trees and opened DEC-1052; `/issues` named DEC-1052 and page two held the POST (2026-10-13).

## MCP servers (project-scoped)

- `scryfall_*` — card oracle text / search / bulk collection. Mandatory for any card claim.
- `commanderspellbook_find_combos` — combo + near-miss lookup (MCP pydantic crash workaround: curl backend, see memory).
- `youtube_*` — deck-tech research.
- `archidekt_*` — publish decks (needs `ARCHIDEKT_AUTH_TOKEN` for writes).
- Find an issue by identifier: `GET /api/companies/{companyId}/issues?q=DEC-1016&limit=3` (filter the rows by `identifier`; `identifier=` and `identifiers=` are ignored). `?parentId=<uuid>` lists children. The list carries no `executionPolicy`; read the monitor by `GET /api/issues/{uuid}` (DEC-1022, 2026-10-13).
- The PATCH response of an issue omits `blockedBy` (it prints `[]` even when a blocker is set); read blockers by `GET /api/issues/{uuid}` before re-sending `blockedByIssueIds` (DEC-1040, 2026-10-13).
- Comments list rows (`GET /api/issues/{uuid}/comments`) are newest-first, like runs (`[0]` is the latest; `[-1]` is the oldest), and carry `authorAgentId` / `authorUserId` with `authorType`; the wake payload's `authorId` is not in that shape. Runs list rows carry `runId`, not `id`. `blockedByIssueIds` is accepted on issue POST (and PATCH); GET echoes `blockedBy` with each blocker's status (DEC-1032, 2026-10-13).

- Setting an issue's last open child to `done` starts a CEO run on the parent within a second (`invocationSource: automation`); a parent with another open child gets no run. Post the parent's close-out right after the child's, or that run finds the parent half-closed (DEC-1030 → DEC-996 run `fad7ef8a`, 2026-10-13).
- To close a chain with no stray run: create the follow-up as a child of the implementing issue first, then PATCH `done` on the grandparent, then the parent, then the review child. A parent that is already `done` gets no last-child run, and the review child is no longer the last open child (DEC-1047, then DEC-1051, then DEC-1054 with DEC-1057 open; no run started, 2026-10-13).
- In mtg-precon-upgrader `delete_branch_on_merge` is off and `main` has no branch protection (2026-10-13). Delete the remote head branch by API at every merge (`gh api -X DELETE repos/DioPires/mtg-precon-upgrader/git/refs/heads/<branch>`); a push to `main` does not block a pull request's merge there.
- mtg-precon-upgrader is a private repository, so each Actions run draws on the account's minutes, and CEO note commits reach `main` many times a day: keep a path filter on every workflow. Decision on DEC-1051 (2026-10-13): no required check and no branch protection on `main`, because GitHub leaves a required check pending when a path filter skips its workflow. The CEO's read of the checks at each merge is the gate.
- `python-tests` is on `main` since `54bbb65` (PR #13). It starts on `scripts/**`, `data/**`, `tests/**`, `pytest.ini` and its own file. Expect `291 passed, 1 skipped, 1001 subtests passed` in CI and `292 passed` with the Scryfall mirror linked. Until DEC-1057 lands, a pull request that changes only `agents/ceo/analysis/dec925/**` or `web/src/lib/__fixtures__/synergy-parity.json` starts no run, so its brief asks for the suite by hand.
- A `pull_request` path filter reads the whole diff of the pull request. A pull request that edits the workflow file starts the job on every push, so no run on it tests a new pattern alone (all five runs for PR #13 came from the workflow file's own pattern). A brief that adds a pattern asks for one draft pull request, based on the feature branch, that touches only a file under the new pattern (DEC-1057, 2026-10-13).
- Before a brief turns a reviewer's list into work, repeat the search on `main`. `git grep -nE 'exists\(\)' origin/main -- 'tests/*.py'` found a fourth skip-or-return guard on a tracked input; the verdict's table named three (DEC-1054 N7 into DEC-1057, 2026-10-13).
- `main` in mtg-precon-upgrader moves every few minutes with CEO note commits, so a whole merge-tree id in a brief is stale at once. Give the reviewer the three-dot diff (`git diff --stat origin/main...<branch>`), the `web` subtree id for a web pull request, and a path-limited guard (`git diff --stat <basis> origin/main -- <paths the suite reads>` prints nothing). A two-dot `git diff origin/main <head>` lists the note commits as changes (DEC-1054, 2026-10-13).
- When a merge changes the tree that an open pull request's CI tests (PR #12 added `tests/__init__.py` under PR #13's `python-tests` job), update that branch before routing its review: `gh api -X PUT repos/DioPires/mtg-precon-upgrader/pulls/<n>/update-branch -f expected_head_sha=<sha>`, then `gh run watch <id> --exit-status`. The review then holds a CI run on the tree that `main` will hold. This repository has hosted runners only, so the update needs no process check (DEC-1051, 2026-10-13).
- Several CEO runs share this checkout. A sibling's `git commit` of a file carries my uncommitted edits to it (commit `bad1820` carried my six `AGENTS.md` edits), and a sibling's unpushed commit leaves `main` diverged. When `git status -sb` reads ahead or behind, do not pull or rebase in the shared checkout. Commit notes in a scratch tree (`git worktree add --detach wt-ceo-notes origin/main`), push `HEAD:main`, remove the tree, and edit lines that the sibling's commit does not touch (DEC-1050, 2026-10-13).
- To carry review figures into a `blocked` follow-up, PATCH its description and `blockedByIssueIds`; do not comment. Those PATCHes started no run on DEC-1024, DEC-1025 or DEC-1032. A comment on an issue whose assignee run is live or queued started no extra run either (DEC-1034, DEC-1031; 2026-10-13).
- In mtg-precon-upgrader `web-ci` starts only on `web/**` and on its own file, but the e2e suite reads `data/` through the preview server (`web/vite.config.ts:9`). Until DEC-1045 item 9 lands, a brief whose pull request changes only `data/` or `scripts/` must ask for `npm run test:e2e` by hand, with the count of its branch point. A description PATCH on a `todo` issue (DEC-1016) started no run. A push of `agents/**` alone starts no CI (DEC-1031 N8, 2026-10-13).
- Web briefs that ask for a height or a screenshot: say "read after `document.fonts.ready`" (a fallback serif read 34 px against 36 px) and "take the shot with `animations: 'disabled'`" (PR #10's evidence PNG caught a chip in the middle of a 0.15 s colour transition) (DEC-1031 N5 and N10, 2026-10-13).
- In mtg-precon-upgrader a pull request's green run can be older than the tree that merges. The run tests the merge with `main` as it stood when the run started, and no rule forces an update. PR #11's run read 59 Playwright cases against `main` at `366518d`; the merged tree read 62 (PR #10 had merged in between). After every web merge, wait for the push run on `main` (`gh run watch <id> --exit-status`) before the close-out, and quote its totals as `main`'s. Before a sentence such as "CI tests the merge with `main`, which gained PR #8, #9 and #10" goes into a record, check the run's `createdAt` against the merge times (DEC-1044, 2026-10-13).
- Setting a blocker to `done` starts an `issue_blockers_resolved` run only for a dependent whose assignee is idle at that second (DEC-1045 started in the same second). For a busy assignee the wake is `skipped` (`reason: other`) and the issue stays `blocked` with every blocker done (DEC-1020, DEC-1024). So: refresh every dependent's description before the `done` PATCH (merge commit, line numbers and totals on the new `main`, the order in the assignee's queue; re-point `blockedByIssueIds` for one that must wait for a sibling). After it, read each dependent, PATCH `todo` and post a short start comment. `GET /api/issues/{uuid}/diagnostics/wakes` and `/queued-comments` show what became of a wake (`deferred_issue_execution`, `executionWait: execution_recovery`, "Your message is saved"); check at the next wake that the run started (DEC-1017 close-out, 2026-10-13).
- A sibling CEO run can push its notes commit as a rebased copy and leave the local `main` on the original, so the local branch diverges from `origin/main` (`80a398f` against `c9b4768`). Check that `git patch-id --stable` is equal for both and that `git diff HEAD origin/main` is empty, then `git reset --keep origin/main`. Do not rebase: the tree holds other runs' edits and the stash is shared (DEC-1044, 2026-10-13).

## Waiting on the shared Mac inside one run

- Foreground `sleep` is blocked in this harness, and a turn that ends on a background wait fails the run. Block on the real condition instead: `caffeinate -w <pid>` returns when that editor or player exits, and `gh run watch <id> --interval 15` returns when a CI run ends. A bounded `for` loop that re-reads `pgrep -x Unity`, `pgrep -f 'MacOS/[E]ternities'` and the CI queue, waits with one of those two, and runs `gh api -X PUT .../pulls/<n>/update-branch -f expected_head_sha=<sha>` in its own body keeps the check and the push in one shell line (DEC-978, 2026-10-13).
- Two green pull requests under strict protection, each with its own CEO run: the one whose `update-branch` came first merges first. The other run waits on that CI run (`gh run watch`), reads the merge, then updates once and merges pinned to the new head. Updating at once costs a second CI run when the first merge lands (PR #132 before PR #131, 2026-10-13).
- `git worktree remove` without `--force` removes a tree whose only extra content is ignored files (builds, Unity's `Library`). Before it, check that no copy the owner uses is a link into that tree (`find <Build> -maxdepth 4 -type l`).
- Before the close-out comment, re-read the wake issue's newest comments: another agent's run can write there while this run waits on CI (DEC-978, Founding Engineer's 09:34Z note).
- Set `HOME="$PAPERCLIP_GITHUB_HOST_HOME"` for every git command in a worktree, not only for commit. A tree made with that `HOME` holds real LFS files, and `git status`, `git diff` or `git add` without it lists every LFS file as changed, because the clean filter is not configured in the sandbox `HOME` (DEC-1038, 2026-10-13).
- zsh does not word-split an unquoted `$var`: `set -- $pair` puts the whole string in `$1`, and the loop's calls go out with bad arguments. Use a shell function with explicit arguments for a per-issue loop (DEC-1026, 2026-10-13).
- In zsh, an unquoted word that starts with `=` is command expansion: `echo ====` fails with "= not found" and stops an `&&` chain. Quote separators (`echo '----'`) (DEC-1038, 2026-10-13).
- In zsh, `$B:web/src/x` applies a history modifier (`:w`, `:c`) to `$B` and git gets a broken path. Write `"${B}:web/src/x"` in `git show` and `git rev-parse` (DEC-1027 and DEC-1044, 2026-10-13).
- A comment has no edit route: `/api/issues/{uuid}/comments/{commentId}` takes GET and DELETE only. To correct my own comment, check that the thread holds nothing newer, DELETE it and POST the corrected body. The route list is `GET /api/openapi.json` (DEC-1038, 2026-10-13).
- Two documents pull requests that edit the same line (the PRD's status line, a §12 row) cannot both branch from `main`. Draft the second in scratch, wait for the first to merge (`gh run watch <id> --exit-status` on its CI run is a foreground wait), then branch from the new `main` (DEC-1014 and DEC-1038, 2026-10-13).
- A run that reassigns its wake issue is cancelled within seconds (`issue_reassigned`). Make every follow-up write that the comment promises ("goes to DEC-X today") before the reassignment PATCH. On DEC-1041 the run of 11:05Z promised two follow-ups, was cancelled, and wrote neither; the gap was found at the merge four hours later. At every close-out, re-read my own earlier comments on the thread for a promised write and check that it exists (2026-10-13).
- Two CEO runs on one hub: a sibling run can post "the brief should list these points" on the hub while this run drafts the brief. Re-read the hub's newest comments in the same step as the POST of a review issue, then grep the posted brief for each listed point. On DEC-1003 the DEC-1041 run listed nine points at 15:05Z, and the hub run opened DEC-1055 at 15:14Z with five of them. The retry run read the brief against the list and added items 12 to 15 (description PATCH and a comment, both 200 on an issue with a live reviewer run) eight minutes into the review (2026-10-13).
- A brief for a delta re-read gives the fix commit's parent as the diff base (`git diff <parent> <fix>`). A base from before a merge of `main` also lists the files that came in with `main` (DEC-1041 N1, 2026-10-13).
- The list for the next PRD v4 and plan erratum is an issue of its own, not a hub comment: find it with `?q=next%20PRD%20v4%20and%20plan%20erratum` (DEC-1040 on 2026-10-13) and PATCH the note into its description.

## Owner cards

- A card that checks a device asks which device in the same card ("what did you scroll with": notched wheel, Magic Mouse, trackpad). On DEC-978 the owner ticked "the wheel zoomed" and the instrument's file held only touch-surface lines; settling it cost a second card.
- Feel work on a device nobody at the Mac can touch (trackpad, wheel, gamepad): brief the first commit as the instrument and make the owner's first check a measurement, not a judgment; the numbers come from the owner's file. On DEC-978, numbers from arithmetic on assumed gesture sizes cost one owner round ("still too slow"); numbers from the file passed at the first check (2026-10-13).
- An owner's "later" on a device check closes the leg: the point goes on the hub's backlog (DEC-950) with the check's steps and the table of what each answer starts, and the owner answers there. Do not park the leg on a monitor for it (DEC-978, 2026-10-13).
- Reading `scroll-parts.txt`: a touch surface writes exact multiples of 0.05, one a frame, with a small sideways part at a gesture's start; a notched wheel writes non-multiples (0.1000061, 0.79, 8.49), two to four frames apart.
- A run that dies on `provider_quota` leaves a `scheduled_retry` run on its issue (`GET /api/heartbeat-runs/{runId}`: `status`, `scheduledRetryAt`, `retryOfRunId`); the time is the provider's reset ("resets 6:50pm Lisbon" = 17:50Z), not a backoff. `POST /api/heartbeat-runs/{runId}/cancel` returns 403 for an agent (board access). Reassigning the issue to another agent cancels the CEO's queued retry on it (DEC-1004, 2026-10-13); a park that keeps the issue with the CEO does not (DEC-1003), so the retry fires as a `retry_failed_run` run that must read the thread first. When routing such a lost hand-back before the retry fires, say in the routing comment what that run should do (nothing), and never write "the retry is cancelled" before reading the run's status back.
- The route `DELETE /api/issues/{uuid}/comments/{commentId}` returns an empty body on 200; `json.loads("")` on it raises. Read the raw bytes and parse only when non-empty.
